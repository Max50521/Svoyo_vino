# Архитектура

Состояние 28.09.2026: 2080 вин, 6240 векторов, Top-1 59/64 на публичном наборе с командной разметкой. Проверенный стенд: Windows, CUDA, локальный PostgreSQL WASM/PGlite; конфигурация обычного PostgreSQL/Docker и Linux-скрипты подготовлены, но требуют отдельной Linux-приёмки.

## Поток запроса

```
фото (multipart "image")
   │
   ▼
web — Nuxt 3 / Nitro, :8080 ─────────────────────────────────────────────┐
   │ 1. приём и валидация (readImage: multipart, magic bytes, ≤15 МБ)     │
   │ 2. RecognitionEngine.recognize(image, k=5)   ← ENGINE=vector|stub     │
   │ 3. ответ: /v1/eval/predict → {"slug"} ; /v1/search → top1/top5/margin │
   └──────────┬───────────────────────────────────────────────┬──────────┘
              │ 1) POST /analyze  2) POST /rerank              │ SQL: визуальный Top-10
              ▼                                                ▼
ml — FastAPI, :8001                                  Postgres 16 + pgvector
   /analyze: нормализация → SigLIP 2 → вектор        wines, wine_embeddings
             ‖ параллельно EasyOCR → текст + координаты
   /rerank:  Top-10 + текст → финальный порядок
```

VectorEngine: `/analyze` (вектор + OCR) → pgvector Top-`RERANK_K` по визуальному скору → `/rerank` → Top-5 по финальному скору. При `OCR_ENABLED=0` — `/embed` и только визуальный скор.

## Слои

| Слой | Где | Что делает |
|---|---|---|
| Нормализация фото | `ml/wine_ml/preprocess.py` | EXIF-поворот → RGB, прозрачность → белый → обрезка белых полей → уменьшение до 1024 → паддинг до квадрата. Одна функция для эталонов, запросов и оценки, чтобы векторы были сопоставимы. |
| Извлечение признаков | `ml/wine_ml/embedder.py` | SigLIP 2 (`google/siglip2-so400m-patch14-384`, 1152-d), fp16 на GPU, L2-нормировка. |
| Поиск по каталогу | `web/server/utils/engine/vector.ts` | косинусное расстояние `<=>` в pgvector по всем видам вина (бутылка + 2 зоны этикетки, `ml/wine_ml/views.py`); score вина = (1 − w)·бутылка + w·лучшая зона этикетки, w = `LABEL_WEIGHT` (0.5); точный перебор (≈6k векторов), Top-5. |
| OCR-переранжирование | `ml/wine_ml/ocr.py`, `ml/wine_ml/text_match.py` | EasyOCR (ru+en); нормализация смешанных алфавитов, разорванных слов, вариантов написания сортов и фамилий. Сопоставляются название, винодельня и сорта. IDF внутри Top-10; text — F-beta (beta=0.5) согласования видимых слов, не F1 качества классификации. Слова с пространственно взвешенной уверенностью <0.35 не создают штраф противоречия. final = visual + α·text − β·conflicts. |
| Выдача карточки | `web/server/routes/v1/wines/[slug]/`, `web/pages/wine/[slug].vue` | карточка вина из таблицы `wines` + фото каталога + необязательное поле `taste_passport`. |
| Уверенность | `web/server/utils/search.ts`, `status.ts` | `score` = итоговый скор; `margin` = score₁ − score₂; `status` = `confident` / `uncertain` / `not_found` по порогам `CONFIDENCE_MARGIN` (по финальному скору) и `NOT_FOUND_SCORE` (по лучшему **визуальному** скору: текст не должен «вытягивать» вино, не похожее на фото). |
| Доп. функционал: «Паспорт вкуса» | `web/server/taste/` (анализатор), `web/types/taste.ts` (типы), `web/components/Taste*.vue`, `Aroma*.vue` (UI) | после найденного slug: чистая функция `buildTastePassport({name, description})` без сети и БД извлекает сладость, кислотность, танины, тело (`known` / `unknown` / `conflict`) и ноты ароматов по 13 семействам; у каждого вывода — точная цитата и id правила `taste-rules@N`. Не участвует в распознавании; сбой анализатора → `taste_passport: null`, карточка остаётся 200. Аналоги (`web/server/taste/analogs.ts`, кеш профилей каталога `web/server/utils/tasteCatalog.ts`): для карточки — по паспорту вкуса, для `not_found` — по сорту из текста этикетки; сбой аналогов не влияет на ответ поиска. Подробнее — [отчёт](reports/taste-passport/REPORT.md). |

## Recognition Engine — точка подключения CV

```ts
interface RecognitionEngine {
  name: string; model: string | null
  recognize(image: UploadedImage, k: number): Promise<RecognitionResult>
}
// RecognitionResult: { candidates: Candidate[], bestVisualScore: number, diagnostics?: Record<string, unknown> }
```

- `StubEngine` — детерминированная заглушка (хеш картинки → реальные slug каталога). Не требует ml и БД; для фронтенда и тестов.
- `VectorEngine` — `/analyze` + pgvector + `/rerank`; при выключенном OCR — `/embed` + pgvector.
- Новый движок (например, с OCR-переранжированием) = новый класс + строка в `getEngine()`. API и фронтенд не меняются.

Контракт ml-сервиса: `POST /embed` (multipart `image`) → `{model, dim, embedding[], embed_ms}`; `GET /health`.
Web проверяет, что `model` ответа совпадает с `MODEL_NAME` индекса, — иначе 503 (защита от смешения векторов разных моделей).

## Данные и офлайн-конвейер

```
data/raw/strapi_output0709.csv + data/raw/strapi/.../uploads
   │ ml/scripts/build_catalog.py      однозначные позиции → data/catalog/{wines.jsonl, excluded.csv, images/}
   │ ml/scripts/load_catalog.py       → таблица wines
   │ ml/scripts/build_index.py        → таблица wine_embeddings (slug, model, vector)
   └ ml/scripts/evaluate.py           → reports/eval-*.md|json
```

Сопоставление: у файла Strapi отрезается `_<hash10>`, имена приводятся к общему ключу. Также разрешаются однозначный снимок бутылки, повторная загрузка, повторное сжатие одного растра. Последнее проверяется в полном разрешении с одинаковыми размерами/альфа-каналом и ограниченными локальными различиями, чтобы не потерять небольшие отличия этикетки. Общие фото нескольких slug сохраняются как `shared_photo` и учитываются как ограничение данных. Исключённые записи: `file_not_found`, `ambiguous_file`, `unreadable_image`.

`wine_embeddings` хранит модель и вид (`full`, `label_mid`, `label_low`) в ключе. «Похожие вина» и поиск двойников используют только `full`.

**Двойники** (`ml/wine_ml/twins.py`): разные вина с близким эталоном (косинус `full` ≥ 0.99), связные компоненты. В синтетическом `evaluate.py` учитываются отдельно. В свежем HTTP-прогоне они не удаляются из 64 известных фото: исключены только 3 исходно спорных записи с меткой `?`/пустой меткой.

`wine_embeddings` хранит модель в ключе — можно держать индексы нескольких моделей и переключаться `MODEL_NAME` без миграции.

## Оценка

- **Синтетическая** (`evaluate.py`): из каждого эталона генерируются «полевые» фото (`augment.py`: крупный план этикетки или бутылка целиком, перспектива, наклон, фон, свет, блик, размытие, JPEG). Метрики Top-1/Top-5, margin, доля «уверенных» ответов и их точность — отдельно для near-duplicates (эталоны, у которых ближайший другой эталон с косинусом ≥ 0.9). Это ориентир, не реальная точность.
- **Реальная публичная**: `scripts/verify_http.py` — все 100 фото через работающий web/API, фиксированные хеши входов, командная разметка, Top-1/Top-5, неизвестные вина, задержки. Закрытой независимой разметки организаторов нет.
- **Контракт кейсодержателя**: `eval/participant_test.sh` против запущенного сервиса.

## Границы устойчивости

Инференс выполняется в отдельном потоке с ограниченной очередью; переполнение получает 503. OCR имеет отдельный ограниченный исполнитель и таймаут, при сбое сохраняется визуальный результат. `/ready` проверяет модель, размерность и полное покрытие трёх видов индекса. Хеши исходных изображений и кода в индексе предотвращают повторное использование устаревших векторов после изменения подготовки данных.

`CONFIDENCE_MARGIN=0.05` — эвристика отрыва после обновления OCR, не калиброванная вероятность. `not_found` остаётся отдельным порогом лучшего визуального сходства 0.75. `/v1/eval/predict` возвращает лучший slug независимо от пользовательского статуса; UI может показать варианты и при правильном Top-1.

## Куда расти

1. Размеченные реальные фото → калибровка `LABEL_WEIGHT`, `OCR_ALPHA/BETA`, порогов уверенности.
2. OCR только по центральной части кадра / меньшему разрешению — быстрее и меньше текста соседних бутылок.
3. Облачный OCR (Yandex Vision) за тем же интерфейсом `OcrEngine.read()`.
4. Дообучение SigLIP 2 (контрастивно, на синтетике/полевых фото) на 4060.
