## 1. Цель и пользовательская польза

Человек стоит перед бутылкой в магазине или уже держит её дома. Он фотографирует этикетку, получает карточку и хочет быстро понять: «Насколько это сладкое, кислое, терпкое и плотное? Какие ароматы описаны? Подойдёт ли мне такой характер вина?»

Существующий путь: сканирование/загрузка → результат распознавания → карточка → полная информация на «Своё Вино». На платформе есть публичный каталог, карточки, рейтинги, похожие вина, винодельни, статьи, события и туры. Новый сценарий не должен зависеть от регистрации, истории сканов или предварительных оценок.

В некоторых карточках портала уже есть гастросочетания, температура и крепость. В нашем CSV нет соответствующих отдельных полей. Работа ограничена двумя выбранными функциями. Личный кабинет, избранное, рекомендации блюд, персональный мэтч, магазинные цены и новые рекомендации вин в этот этап не входят.

Пользователь должен понять основные свойства за 5–10 секунд, а при желании раскрыть объяснение. Все характеристики относятся к открытой карточке; они не являются измерением содержимого бутылки по фотографии.

## 5. Функция №1: «Какое оно на вкус»

Покажи четыре характеристики:

- **Сладость**: подтверждённая категория словами; шкалу для игристых не смешивай бездумно со шкалой тихих вин.
- **Кислотность**: низкая / средняя / высокая при достаточном текстовом основании.
- **Танины**: показывай выраженность, только если она описана. Качество «бархатистые» или «округлые» можно вывести отдельной словесной характеристикой без выдуманного уровня.
- **Тело вина**: лёгкое / среднее / полное. Пояснение для новичка — «Насколько плотным вино ощущается во рту».

Важно различать тело, насыщенность аромата и интенсивность вкуса. «Интенсивный аромат» не означает полное тело. «Мягкий вкус» не означает низкую кислотность. Если название «Тело вина» сочтёшь сложным, используй «Плотность вкуса» с тем же объяснением; не заменяй его неопределённой «насыщенностью» во всех контекстах.

Для подтверждённого уровня используй три визуальных маркера и обязательную словесную подпись. Не делай вид, что есть точность до пяти баллов или десятых. Если данных недостаточно — нейтральное «В описании не уточнено», без нулевого значения и без активных маркеров. Отсутствие данных по танинам у белого вина не означает доказанное отсутствие танинов.

Краткое резюме в одну строку собирай из подтверждённых фактов. Оно не должно противоречить шкалам или вводить новые выводы. Если фактов мало, оставь компактную карточку без искусственного заполнения.

Добавь понятные справки по нажатию на характеристику: что означает кислотность, танины, тело. Это общие пояснения терминов, а не персональные советы.

## 6. Функция №2: «Ароматы и вкусовые ноты»

Первый уровень: до шести конкретных нот с оригинальными контурными иллюстрациями и подписями. Размер иллюстраций примерно 48–64 px; текст читается без увеличения. Для одного найденного аромата показывай один; минимальное количество не должно приводить к выдумкам.

Примеры семейств: цитрусы; садовые/косточковые фрукты; красные ягоды; тёмные ягоды; тропические фрукты; цветы; травы; специи; орехи; древесные оттенки; сладкие ароматические ассоциации; минеральные/дымные оттенки. Точный словарь согласуй с реальными описаниями. Если источник говорит только «ягоды», показывай «Ягоды», не превращай их в вишню и смородину.

Второй уровень: кнопка **«Раскрыть карту ароматов»**. Покажи компактную интерактивную карту семейств, вдохновлённую круговыми схемами книги. На широком экране возможны равноправные дуги/сектора вокруг названия вина; на телефоне — простые группы с горизонтальными подписями. Не заставляй человека читать мелкие повёрнутые слова по окружности. Карта должна дополнять краткий список и показывать группировку, а не быть обязательным препятствием.

Площадь сектора не означает процент аромата. Наличие в тексте и частота упоминания не равны интенсивности. Используй равные декоративные сектора либо прямо обозначенную группировку без количественного смысла. Если нот слишком мало, достаточно списка без пустого большого круга.

Нажатие на ноту/семейство раскрывает связанные ноты и исходную фразу. Одно объяснение открыто за раз. Доступны клавиатура, видимый фокус и закрытие. Рисунки не должны быть единственным носителем информации.

Короткая подпись под блоком: **«Ассоциации из описания вина, а не добавленные ингредиенты»**. Иллюстрации не должны превращаться в сведения о составе, аллергенах или наличии фруктов в бутылке.

## 7. Правила достоверности — обязательны

Используй описание конкретной карточки и явные характеристики в названии. `slug` оставь идентификатором, а не универсальным источником вкуса. Сорт — метаданные для карточки, не основание автоматически дорисовать недостающий профиль. Онлайн-парсинг портала при каждом запросе и массовое обогащение из книги не нужны.

Для каждого вывода сохраняй происхождение: поле, точную подстроку исходника, правило/версию анализатора. Пользователь видит человеческое объяснение и цитату в раскрытии **«На чём основано»**. Технические имена правил в интерфейс не выводи.

Обработай:

- русские окончания, «ё/е», регистр, дефисы, пунктуацию;
- границы слов и длинные совпадения прежде коротких: «полусухое» не «сухое», «чернослив» не «слива», «сливочный» не «слива», «цвет» не «цветочный аромат»;
- локальный контекст и отрицания: «без высокой кислотности» не даёт высокую кислотность; «танины не выражены» не даёт выраженные танины;
- фразы неопределённой интенсивности: «гармоничная», «хорошая», «сбалансированная» кислотность не равны средней;
- разграничение признаков: «высокая кислотность и мягкие танины» не переносит «высокая» на танины;
- ароматы и другие разделы: «к вишнёвому пирогу» не аромат вишни; «выдержано в дубе» не автоматически ваниль; «сладкие ароматы мёда» не сладкое вино;
- конфликт: несовместимые явные утверждения об одном признаке дают состояние «противоречивые данные», а не произвольного победителя;
- пустое/слишком общее описание, опечатки, дубли, HTML и длинный текст.

Не выводи pH, г/л, проценты сахара, «достоверность 97%» или лабораторную точность. Не рассчитывай отсутствующие свойства по фотографии. Не добавляй характеристики из фото книжных страниц в данные вина. Не приписывай конкретному вину общие показатели сорта.

## 8. Архитектура и устойчивость

Сделай чистую детерминированную функцию вида `buildTastePassport(wine)`, которая возвращает стабильный результат без сети. Словарь, правила и типы выдели отдельно. Версионируй правила. Не привязывай корректность к порядку случайного обхода словаря.

Предпочтительный совместимый API: добавить необязательное поле `taste_passport` к ответу `GET /v1/wines/:slug`, сохранив все старые поля. Внутри — `version`, `summary`, шкалы, ноты и evidence. Для шкал различай состояния `known`, `unknown`, `conflict`; неизвестный уровень хранится как `null`. Подготовь типы в `web/types/api.ts` и согласуй сервер с UI. Не возвращай stack trace при ошибке анализатора.

Ошибка нового модуля не должна превращать рабочую карточку в 500: базовая информация продолжает отображаться, паспорт аккуратно скрывается или показывает недоступность. Это не должно маскировать настоящую ошибку БД или менять существующие 404/503. Фронтенд должен работать и с ответом старого сервера, где поля `taste_passport` вообще нет.

В интерфейсе выдели компоненты по назначению, например `TastePassport`, `TasteScale`, `AromaNotes`, `AromaMap`, `TasteEvidence`. Не создавай сложную абстрактную платформу. Иллюстрации и справки локальные. Никакого генератора изображений во время запроса пользователя; SVG-ассеты создаются один раз и переиспользуются.

Паспорт относится к текущему slug и должен обновляться при переходе к другому кандидату без старых цитат и ароматов. Предупреждение о неуверенном распознавании и выбор Top-5 остаются заметными. Для `not_found` не генерируй паспорт несуществующего вина. Блок «Похожие по этикетке» сохраняет свой смысл и название: CV-сходство не становится вкусовым сходством.

## 9. Компоновка и удобство

Карточка: название/винодельня/фото → основные сведения → две функции паспорта → исходное описание → существующие дальнейшие действия. При неуверенном результате предупреждение и выбор кандидата должны быть доступны раньше подробной карты ароматов. Не закрывай важные действия большим декоративным блоком.

Уместна локальная корректировка размеров фотографии на мобильном экране, чтобы новый полезный контент не прятался слишком далеко. Сохрани узнаваемую карточку и всю прежнюю информацию. Добавь ссылку «Полная карточка на Своё Вино» с безопасно сформированным URL для slug. При недоступности внешнего сайта локальный паспорт продолжает работать.

Проверь ширины 360, 390, 768 и 1440 px. Не должно быть горизонтального скролла, обрезанных подписей или наложения длинных названий. Области нажатия — не меньше 44 px, текстовые подписи доступны без hover, контраст достаточен, смысл не зависит только от цвета. Учти клавиатуру, экранный диктор, reduced motion и раскрытия после SSR без hydration errors.

**Этап B — данные и правила.** Создай типы, словарь, анализатор и содержательные unit-тесты. Покажи результаты на настоящих примерах. Исправь неверные извлечения до отрисовки. Сохраняй evidence как подстроку исходного поля.

**Этап C — функция 1.** Подключи совместимый API, шкалы, краткое резюме и объяснения. Проверь пустые данные, конфликты и ответ старого сервера.

**Этап D — функция 2.** Создай согласованные SVG-иллюстрации, список нот, раскрываемую карту и доступное взаимодействие. Сначала мобильная компоновка, затем широкая.

**Этап E — интеграция и защита от регрессий.** Проверь переходы между кандидатами, прямое открытие ссылки, повторную загрузку, not_found, 404, 503 и ошибку нового анализатора. Прогони существующие проверки, относящиеся к изменениям, и production build. Не меняй ML ради возможности пройти UI-тест.

**Этап F — приёмка и передача.** Сохрани скриншоты, результаты команд, отчёт об извлечении и ограничения. Обнови README и продуктовое ТЗ, чтобы не осталось обещания полной заполненности характеристик. Предоставь коммит/ветку и краткое описание изменений; если доступна публикация, отправь feature-ветку и подготовь PR. Не сливай автоматически в main.

## 11. Обязательные проверки и критерии приёмки

Проверь примеры, различающие правильное поведение и правдоподобную ошибку:

1. «Полусухое» не превращается в «сухое».
2. «Без выраженных танинов» не даёт высокую танинность.
3. «Сливочная текстура, аромат чернослива» не даёт аромат сливы из первого слова.
4. «Насыщенный рубиновый цвет, лёгкое тело» даёт лёгкое тело.
5. «Аромат мёда, сухое вино» не превращается в сладкое.
6. «Гармоничная кислотность» не заполняется средним уровнем.
7. «Выдержано в дубе, подавайте к вишнёвому пирогу» не дорисовывает ваниль и вишню.
8. Противоречивые уровни, пустой текст, XSS-строка и старый API безопасно обрабатываются.
9. Каждая нота и шкала имеет проверяемый источник; повторный запуск даёт тот же результат.
10. Переход к другому slug обновляет весь паспорт; исходный оценочный API сохраняет ровно `{"slug":"..."}`.

Если доступен полный каталог, обработай все записи и посчитай отдельно по каждому признаку: `known / unknown / conflict`; число вин с хотя бы одной нотой; распределение нот и ошибки. Не считай полноту по искусственному требованию «90%»: отсутствие сведений допустимо, выдуманные сведения — нет.

Вручную проверь 50 разнородных карточек: разные цвета, сорта, длины описаний, игристые/тихие при явной маркировке, неполные и спорные данные. Проверяй и ложные находки, и пропущенные явные факты; покажи таблицу «исходная фраза → результат → оценка». При ограниченном наборе укажи реальное число проверенных карточек. Не объявляй словарное извлечение сенсорной экспертизой сомелье.

Ориентиры команд: в `web/` — `npm ci`, `npm test`, `npm run typecheck`, `npm run build`; Python-тесты — по README и доступному окружению. Браузерные проверки должны включать открытие раскрытий и смену карточки, а не только screenshot главной страницы. Для полного live-прогона нужен реальный стенд; при его отсутствии явно пометь эту часть как непроверенную.

Замерь отдельное время анализатора и дополнительный вес ресурсов. Новые функции не участвуют в распознавании, не вызывают сеть и не загружают тяжёлую библиотеку графиков ради нескольких дуг. Секреты, веса, архив датасета и частные фотографии в коммит не включай.

## 12. Что вернуть в конце

- рабочую реализацию двух функций и изменённые файлы;
- ветку/коммит или PR;
- скриншоты: телефон и desktop, богатый профиль, неполные данные, раскрытая карта;
- выполненные команды и реальные результаты тестов;
- отчёт по покрытию и проверке источников с точным знаменателем;
- короткую инструкцию запуска и честный список того, что не удалось проверить;
- двухминутный сценарий демонстрации: фото → найденное вино → шкалы → рисунки нот → объяснение → полная карточка портала.

Критерий успеха: пользователь быстро понимает характер конкретного вина, может проверить происхождение выводов, удобно пользуется карточкой на телефоне, а существующее распознавание и API продолжают работать.
